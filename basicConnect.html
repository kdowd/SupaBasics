The two lines underneath everything

You have used these two lines on every page without stopping to look at them. Now let's take them apart: why we have to fetch a library at all, and what createClient() is actually doing when we hand it a URL and a key.

The two lines: 

<!-- 1. Fetch the library from a CDN -->
<script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.117.3/dist/umd/supabase.js"></script>

// 2. Turn your settings into a working client
const db = supabase.createClient(SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY);
Question one

Why do we need a library at all?

Because the browser has never heard of Supabase. There is no built-in supabase command in JavaScript — if you typed supabase.createClient() in a blank page, you would get ReferenceError: supabase is not defined. A browser only ships with general-purpose tools: fetch, JSON, the DOM. Everything else is something you add.

You could talk to Supabase by hand. It is only HTTP:

// Doing it manually, with no library. This really works.
const response = await fetch(
  'https://decwucuwqnzrxzbxxifu.supabase.co/rest/v1/penguins?select=*&limit=10',
  { headers: {
      apikey:        'sb_publishable_...',
      Authorization: 'Bearer sb_publishable_...'
  }}
);
const rows = await response.json();

That is genuinely all page 1 did under the bonnet. But look at what you now own: building every URL by hand, encoding every filter into a query string, setting two headers correctly on every single request, remembering to swap the Authorization header for a JWT after login, catching expired tokens and refreshing them, storing the session, and parsing error bodies yourself.

The library is a wrapper around exactly that. It is not magic and it is not a server — it is a few hundred kilobytes of JavaScript that writes the boring HTTP for you, and gives you one object to hold.

What you get back is one object with everything on it. That is why the same db could do db.from(...) on page 1, db.auth.signInWithPassword(...) on page 3 and db.rpc(...) on page 4 — database, authentication and functions are all methods hanging off the client you built once.

1

Why a CDN instead of downloading it?

jsdelivr is a mirror of npm, the public package registry. That single <script> tag fetches the exact file the Supabase team published, from a server near the student. No npm install, no node_modules, no build step, no terminal. Double-click an HTML file and it works — which is the whole reason this workshop can exist without teaching a toolchain first.

2

Why @2.117.3 and not just @2?

@2 means “whatever the newest version 2 happens to be today”. That is convenient, and slightly dangerous in a classroom: the page that worked in your lesson plan can behave differently next month through no change of yours. Pinning the exact version makes the class repeatable. Update it deliberately, not accidentally.

3

Why the /dist/umd/ build?

Packages ship several builds for different situations. The UMD build is the friendly one: it defines a single global variable called supabase, so a plain <script> tag is enough and you can use it from any other script on the page.

The ESM build (dist/index.mjs) is what modern bundlers prefer, but it needs import statements and either a build tool or an import map — an extra concept before the first query. We will take the global.

4

Order matters

The library must load before any script that uses it. That is why every page in this project has the same three lines at the bottom, in the same order: the SDK, then supabase-config.js, then the page's own code. Put them the other way round and you get supabase is not defined — the single most common error in this workshop.

Question four

What createClient() does

Two arguments in, one object out. That is the whole function. 

const db = supabase.createClient(
  'https://decwucuwqnzrxzbxxifu.supabase.co',    // 1. WHICH project
  'sb_publishable_ONnalS_8pdIUH2Qrsz67CA_...'     // 2. WHICH key
);
1

The URL — which project am I talking to?

This is your project's address, found in the dashboard under Project Settings → Data API. It is public information. Knowing the address of a building is not the same as being allowed through the door.

2

The key — on whose behalf?

The publishable key is designed to be shipped inside browser code. It is not a password. It tells Supabase which project is asking on behalf of a visitor who has not logged in yet, and it resolves to the anon role — the one your insert policy on page 2 refused.

Never put a secret or service_role key here. Those ignore RLS completely and would hand every visitor the keys to the database.

3

The result — a SupabaseClient

createClient() is a constructor, not a connection. It hands back an object — we verified it is a real SupabaseClient instance — carrying your URL and key plus a set of ready-made method groups. It takes three parameters; the third is an options object you will probably never need at this level.

The clever part: one URL becomes five. You supply the address once, and the client works out every service endpoint from it — the database, the login service, realtime websockets, file storage and edge functions. Look at the https:// versus wss:// and the /rest/v1, /auth/v1 paths in the inspection above. Those are not things you ever type; the library derives them.

The bit that surprises everyone

createClient() does not connect to anything

It makes no network request at all. It is pure configuration — it stores your URL and key in an object and returns it. We proved this by handing it a domain that does not exist: 

supabase.createClient('https://nonsense.invalid', 'fake-key')
// -> no error. It happily builds a client for a domain that has never existed.

The connection happens later, when you first use the client — the moment you call .from('penguins').select() and await it.

Why this matters when something breaks. If a page does nothing, students instinctively go and check the createClient line. That line is almost never the problem — it cannot fail on a typo in the URL, because it never contacts the server. Debug the first query, not the client. The error you want is on the query.

The only two things it checks

Give it an empty string and it does finally complain. These are the real messages, and both are worth recognising instantly: 

supabase.createClient('', '')
// throws:  supabaseUrl is required.

supabase.createClient('https://your-project.supabase.co', '')
// throws:  supabaseKey is required.

Those are thrown, not returned — the only two exceptions in the whole story, because the client cannot be built at all. Press Try the two mistakes above to see them caught and printed live.

And everything after that returns errors instead of throwing. This is the habit from page 1, and it never stops being true. A query to a domain that does not exist does not raise an exception — it hands you an error object: 

const { data, error } = await db.from('penguins_rls_on').select();

// Nothing there?        data: null, error: { message: 'TypeError: Failed to fetch' }
// Table missing?        data: null, error: { code: 'PGRST205', message: "Could not find
//                                          the table 'public.x' in the schema cache" }
// Policy refused you?   data: null, error: { code: '42501', message: 'new row violates
//                                          row-level security policy' }
// All good?             data: [ ...rows ], error: null

if (error) {
  console.error(error.message);   // <- the line that saves you
} else {
  console.log(data);
}
How we did it here

Why we wrote it once, in one file

Every page in this workshop loads the same third line, and it does the createClient call exactly once: 

// supabase-config.js — loaded by all five pages
const SUPABASE_URL = 'https://decwucuwqnzrxzbxxifu.supabase.co';
const SUPABASE_PUBLISHABLE_KEY = 'sb_publishable_...';

window.db = supabase.createClient(SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY);

Duplicating those two values across five pages would mean five places to change when the project moves, and five chances to leave one behind. Storing the client on window.db also means you can open the console on any page, type db, and see it.

Worth knowing: creating a client twice is harmless — page 5 does it again deliberately, to show you the call. Each client is just an independent object with the same settings. It is not a connection, so there is nothing to exhaust or close.
