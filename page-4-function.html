Calling a database function from the browser

So far we have only ever asked Supabase for tables. This page asks it to run a piece of SQL we wrote ourselves — a function called first_penguins(), living inside the database, returning the first ten penguins.

RPC stands for Remote Procedure Call: you name a function and pass it some arguments, and the server runs it for you. Supabase exposes every function in your public schema at a URL like /rest/v1/rpc/first_penguins, and supabase-js wraps that up as db.rpc().

Both halves

The function in SQL, and the call in JavaScript

Two files, two languages. The first lives in your database; the second in the page.

1 · The function — created once, in the SQL Editor

create or replace function public.first_penguins(row_limit integer default 10)
returns setof public.penguins_rls_on
language sql
stable
security invoker
as $$
  select *
  from public.penguins_rls_on
  order by id
  limit row_limit;
$$;

2 · The call — runs in the browser

// Supabase wraps the whole HTTP request for us.
const { data, error } = await db.rpc('first_penguins', {
  row_limit: 10            // becomes the function's argument
});

if (error) {
  console.error('The function call failed:', error.message);
} else {
  console.log('Got', data.length, 'rows from the function');
  console.table(data);
}

Compare the two styles. The table read on page 1 was db.from('penguins').select('*') — “give me a table, and I will filter it”. This is db.rpc('first_penguins') — “run this procedure”. Use a function when the logic belongs on the server: several statements, a calculation, a rule you refuse to trust the browser with.

Reading the definition

Five words worth understanding

1

returns setof public.penguins_rls_on

The result is a set of rows shaped exactly like that table. Using the table name as the return type means the columns can never drift: add a column to penguins_rls_on later and the function returns it automatically.

2

language sql

Plain SQL instead of PL/pgSQL. Postgres can often fold a simple SQL function straight into the calling query, which makes it the fastest option. You only need PL/pgSQL when you want variables, loops or IF statements.

3

stable

“This function reads but never writes.” It lets the planner call it once and reuse the answer. The full set is immutable (same inputs, same answer always), stable (reads data, does not write — ours) and volatile (may write, or may differ each call). Marking a writing function stable is a lie that produces baffling bugs, so this line is not decoration.

4

security invoker

The one that matters for this workshop. The function runs with the permissions of whoever called it, so Row Level Security still applies inside it. A student who calls this function sees only the rows their own policies allow.

The alternative, security definer, runs the function as its owner — usually the postgres superuser — and therefore bypasses RLS completely. That is a door around every policy you wrote. It is occasionally the right tool, and it always deserves a second look. (A view behaves like definer by default, which surprises people; you have to ask for with (security_invoker = true) to make a view respect the reader's policies.)

5

grant execute — the third gate

You have now met three separate gates in this workshop: grants (may this role touch the object?), policies (which rows?), and now execute (may this role run this function?). Postgres grants EXECUTE on new functions to PUBLIC by default, so things usually just work — which is exactly why forgetting it is so confusing when it does not. If one role gets a 404 and another works, look here.

Why bother?

When a function beats a table read

Use a table read when… Use a function when…
db.from('t').select() db.rpc('fn')
You want rows, and the browser is allowed to choose the filtering, sorting and paging. You want the database to decide. The browser asks a question, not for a table.
Simple reads, and RLS already expresses who may see what. Several statements, joins, aggregates or a calculation that would be silly to reimplement in JavaScript.
Anything a student could safely be allowed to write themselves. Logic you do not want to trust the client with — a total, an eligibility check, a rule.
— A writable operation that must always do a second thing, like insert a row and stamp an audit record.

A function is not automatically a security boundary. Everything from pages 1–3 still applies. Because this one is security invoker, RLS decides which rows it can see — if penguins_rls_on had no select policy, this function would faithfully return zero rows and report success. Wrap your logic in a function and you have organised it, not protected it.

Two things that catch people out. First, PostgREST keeps a cache of what exists, so a brand-new function occasionally 404s until you run notify pgrst, 'reload schema';. Second, you can pass arguments the function does not have, or omit ones it requires, and PostgREST reports PGRST202 — “could not find the function with that signature”. The error is about the arguments, not about the function being missing.

Your parameter has a default. Because the definition says default 10, you can also call it with no arguments at all and get ten rows. Try it in the console: await db.rpc('first_penguins').

Try it yourself

Console exercises

// The call this page makes
await db.rpc('first_penguins', { row_limit: 10 })

// Just three rows
await db.rpc('first_penguins', { row_limit: 3 })

// Omit the argument entirely - the `default 10` kicks in
await db.rpc('first_penguins')

// A deliberately wrong argument name: read the error carefully
await db.rpc('first_penguins', { limit: 3 })
// -> PGRST202. The function exists; the SIGNATURE does not match.

// A function that does not exist
await db.rpc('no_such_function')

// Same data, the table way, for comparison
await db.from('penguins_rls_on').select('*').order('id').limit(10)
