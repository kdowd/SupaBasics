Two doors, exactly the same data

On page 1 we read a table that had no security at all. Now we run the same requests against two versions of that table — one still unlocked, one with Row Level Security switched on — and watch what changes.

The one idea on this page: switching RLS on does not mean “nobody can read my data”. RLS decides which rows each operation may touch, and it is your policies that decide. Get the policy right and the public data stays public while the write access disappears completely.

Under the hood

Three things to notice

1

RLS on did not break reading

Both tables returned the same number of rows. The policy for select using (true) says “every row is readable by everyone” — which is exactly what it did. If you had enabled RLS and written no policy at all, the same query would have returned zero rows and no error. That silence is what makes RLS so easy to get wrong at first.

2

Insert shouts. Update and delete whisper.

A blocked INSERT fails loudly — “new row violates row-level security policy” — and you get an error you can catch. But a blocked UPDATE or DELETE simply matches zero rows and reports success. There is no exception. This is why “my update runs but nothing changes” is one of the most common RLS bugs in the wild.

3

You never wrote a rule that forbids anything

Look back at the SQL: there is one policy, and it only ever grants reading. Writing is blocked not because we banned it, but because we never permitted it. RLS starts from deny and you add access one policy at a time — which is the opposite of how most people assume security works.

Where this is going. A policy you write can be permissive or restrictive, and those words describe how policies combine, not how strict they are — multiple permissive policies are OR-ed together, and restrictive ones are AND-ed on top. That distinction matters on page 4, when we start asking auth.uid() who is actually logged in.

Grants and policies are two different gates. A policy cannot give access that a grant withholds, and a grant cannot get you past a policy. This page also runs grant select, insert, update, delete … to anon, so on penguins_rls_on the grant permits writing and the policy is what refuses it. If the grant were missing you would get error 42501 instead. Worth knowing which gate you are hitting.

Reference

What the setup script actually did

The three lines that matter. The full script, including the disposable table copy, is in setup-page2.sql. 

-- Two separate gates: FIRST the grant, THEN the policy.
grant select, insert, update, delete
  on public.penguins_rls_on to anon, authenticated;

-- Every table starts closed.
alter table public.penguins_rls_on enable row level security;

-- ONE permissive policy, granting reading to everyone.
-- Permissive policies are OR-ed together, so they can only widen access.
create policy "Penguins are readable by everyone"
  on public.penguins_rls_on
  for select to anon, authenticated
  using ( true );

-- And deliberately nothing for insert / update / delete.
-- No permissive policy for an operation = Postgres denies it.

Why the page can't show you the policy list. The REST API exposes tables and functions — not Postgres system catalogs like pg_policies. So this page proves the difference behaviourally instead of reading the config. To see the policies themselves, run the verification queries at the bottom of setup-page2.sql in the SQL Editor; the permissive column there is the OR/AND distinction in the catalog.
