Logging in: swapping an anon key for a JWT

On page 2 we proved that only authenticated users may insert into penguins_rls_on. Now we make the browser become one — and look at exactly what the server sends back when we do.

The whole page in one sentence: logging in does not change your policy, and it does not change your key. It changes the Authorization header on every request from an anonymous key into a signed token that says “I am admin@admin.com, and my role is authenticated.” Postgres reads that role, and your insert policy finally matches.

Step two

Try the thing that was forbidden

On page 2 this exact insert failed while signed out. Press the button now — signed in — and watch it succeed. Same policy, same URL, same publishable key. The only thing that changed is who the request claims to be.

You gave INSERT but not DELETE. Your table has a select policy and an insert policy, and nothing else — so once a row is in there, nobody can remove it through the API, including you while logged in. We proved that earlier: the delete came back HTTP 200 with an empty list, reporting success while deleting nothing.

That is RLS being per-operation, and it is worth saying out loud in class: each of select, insert, update and delete is permitted separately. Clear up test rows in the SQL Editor: 

-- remove the rows page 3 adds during class
delete from public.penguins_rls_on
where species = '__TEST_LOGIN__';

The better fix: let students delete their own test rows

You could hand authenticated a delete policy with using (true), but stop and think about what that means: any logged-in user could delete all 344 penguins with one line. true is the most dangerous word in a policy.

Instead, give delete a real condition — one that only matches the rows this page creates: 

create policy "Students can delete their own test rows"
  on public.penguins_rls_on
  for delete
  to authenticated
  using ( species = '__TEST_LOGIN__' );

Now a logged-in student can tidy up after themselves, but the using clause means a delete aimed at a real penguin matches zero rows — silently, as always. You get a self-cleaning classroom without opening the door, and it is a perfect preview of page 4, where true is replaced by auth.uid() = user_id.

Doing it in the dashboard instead: Database → Policies → New Policy → Create a policy from scratch. Pick the DELETE command, tick the authenticated role, and paste species = '__TEST_LOGIN__' into the USING expression box. Leave the WITH CHECK box empty — delete has no new row to check, which is why Supabase greys it out.

The explanation you asked for

What a JWT actually is

JWT stands for JSON Web Token. It is just a string with three parts separated by dots: 

eyJhbGciOiJFUzI1NiIsImtpZCI6...
1

It is encoded, not encrypted

Each part is Base64URL text — a way of writing bytes using only safe characters. It is not secret and not scrambled. Anyone holding the token can read every claim inside it, which is exactly why this page can decode yours and print it below. A JWT is a wristband, not a sealed envelope.

2

The third part is a signature, and that is the point

Supabase signs the first two parts with a private key that never leaves their servers. Your project uses ES256 (ECDSA over the P-256 curve); the kid in the header names which key was used. Change a single character of the payload and the signature no longer matches, so the server rejects it. You can read a JWT freely, but you cannot forge one — which is why the browser is allowed to hold it.

3

One claim does all the work: role

The payload contains "role": "authenticated". When a request arrives with this token, PostgREST verifies the signature, reads that claim, and runs the query as the Postgres role named authenticated. Your policy says to authenticated, so now it matches. That is the entire mechanism connecting “I logged in” to “the database let me write”.

What the claims mean

ClaimMeaning
subThe user's permanent id (a UUID). This is the value page 5 will compare against a user_id column.
roleauthenticated. This single claim is what your RLS policy matches on.
aud“Audience” — who the token is for. Also authenticated.
exp / iatExpiry and issue time. Exactly one hour apart here, so the access token is short-lived on purpose.
emailHandy for display — never for authorization. Use sub; people change email addresses.
aal / amrHow strongly you proved who you are, and how you did it — here aal1 via password. A second factor would raise this to aal2.
session_idIdentifies this one login, so the server can revoke it without affecting your other devices.
is_anonymousfalse. Supabase supports real anonymous sign-in, and this flag is how you tell them apart.
The bit that usually confuses people

Two headers, two completely different jobs

Every request to Supabase carries two identity headers. Students very often assume the publishable key is what does the authorising. It is not. 

# BEFORE logging in — both headers are the same public key
apikey:        sb_publishable_OnNa...      # which project? always this
Authorization: Bearer sb_publishable_OnNa... # who? nobody -> role: anon

# AFTER logging in — only Authorization changed
apikey:        sb_publishable_OnNa...      # unchanged
Authorization: Bearer eyJhbGciOiJFUzI1...   # who? admin@admin.com -> role: authenticated

apikey says which project. Authorization says who is asking. When you are signed out, Supabase falls back to treating the publishable key itself as the identity, which resolves to the anon role — the exact role your insert policy does not mention. Signing in only ever changes the second line.

Where does it live?

The session survives the page reload

supabase-js saved that session in your browser's localStorage, under a key named after your project: 

sb-decwucuwqnzrxzbxxifu-auth-token

Open DevTools → Application → Local Storage and you will find it sitting there as JSON: the access token, the refresh token, the user object and an expiry timestamp. Reload this page and you will still be logged in — because getSession() reads that entry before any network request happens.

This is why “just hide the button” is not security. A student can open the console, call db.from('penguins_rls_on').insert(...) directly, or paste the token into their own script — and it will work if the token is valid. No amount of front-end hiding changes that. The only thing standing between a logged-in user and your data is RLS. Treat every check in the browser as a courtesy to the user, never as a defence.

Why is it safe to keep a token in localStorage? Because the token is short-lived (one hour) and cannot be forged. If it leaks, the damage is bounded and the session can be revoked server-side via its session_id. The refresh token is the longer-lived secret, and Supabase rotates it on use.

Keeping it alive

Access tokens expire. Refresh tokens renew them.

// Signing in returns TWO tokens, not one.
const { data, error } = await db.auth.signInWithPassword({ email, password });

data.session.access_token    // JWT - expires in 1 hour, proves who you are
data.session.refresh_token   // longer-lived - used ONLY to get a new access token

You will never see this happen, because supabase-js has autoRefreshToken switched on by default. Roughly five minutes before the access token expires, it quietly POSTs the refresh token to /auth/v1/token?grant_type=refresh_token and receives a brand-new access token. Press Force a token refresh above to do it by hand and watch the token change.

Consequence for testing: because the browser silently renews tokens, “I deleted the user but they still seem logged in” is a real thing you will hit. Sign out properly, or clear the localStorage entry.

Two ways to ask “who am I?”

MethodWhat it doesTrust it for…
getSession() Reads the stored session locally. Instant, no network. Showing the user's name in the corner.
getUser() Asks the auth server to validate the token, every call. Anything that matters. It cannot be faked by editing localStorage.

And for real authority, neither of them is the answer — RLS is. Both of these run in the browser, where the user controls everything. Your policies run in Postgres, where they do not.

// -> 42501, exactly like page 2

// Log back in and the same line works
await db.auth.signInWithPassword({ email: 'admin@admin.com', password: '...' })
await db.from('penguins_rls_on').insert({ species: 'signed in' })
